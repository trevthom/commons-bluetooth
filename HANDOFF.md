# HANDOFF — Commons-Bluetooth

Everything needed to change this safely.

## The one idea

Commons was a server plus clients. This is **a set of devices that each hold the
same signed event log**. A community's state is a pure function of its events, so
two devices with the same events show the same community. No process is
authoritative.

The browser is unchanged in spirit: it asks the node on its own device for state
and posts actions to it. That traffic is loopback-only and is *not* how parties
communicate. Parties communicate over the transports in `mesh/transports/`.

## Wire protocol

```
0     magic 0xCB
1     version 1
2     type
3     ttl            (relays decrement only this byte)
4..5  payload length (LE)
6..13 sender peer id (8 bytes)
14..29 packet id (16 bytes = sha256(type || payload)[:16])
30..  payload
```

Types: `HELLO=1`, `ENC=2` (link-local encrypted), `ENC_EVENT=3` (relayed),
`FRAG=4`, `PING=5`, `PONG=6`.

`FRAG` payload is `fid(8) idx(u16) total(u16) data`, with 700-byte chunks. The
reassembler is bounded and rejects out-of-range indices.

A packet id is over type+payload, **not** the TTL, so a relay can decrement the
TTL without invalidating dedupe. A packet whose id does not match its payload is
dropped before anything else happens.

### Handshake

Both ends send `HELLO` the moment a link opens:

```json
{ "v":1, "peer":"<8-byte hex>", "key":"<account key>", "pub":"<ed25519 b64url>",
  "eph":"<x25519 public b64url>", "nonce":"<16 bytes b64url>", "groups":["…"],
  "name":"ana-laptop", "ts":1710000000000, "sig":"<ed25519 over the rest>" }
```

Checks: the signature verifies, and `key == b32(sha256(pub)[:10], 16)`. The link
key is `HKDF(X25519(eph, peer_eph), salt=sort(nonceA,nonceB), "commons-bluetooth/link/v1")`.
After that every frame is `ENC`/`ENC_EVENT`:

```
[u32 counter][12-byte iv][16-byte tag][ciphertext]
```

The counter must strictly increase (replay protection). The AAD is
`type || sender id from the header` — derived from the packet, never from the
receiver, so both sides compute the same bytes.

### Events

```json
{ "v":1, "id":"<sha256 of the unsigned body>", "gid":"<16 hex>",
  "kind":"msg|edit|delete|react|vote|pin|unpin|post|post_edit|post_reply|…",
  "pub":"<ed25519>", "key":"<account key>", "ts":1710000000000,
  "hlc":"0001710000000000.0000.KEY", "body":{…}, "sig":"<ed25519>" }
```

`hlc` is `wall.counter.key`; ordering events by it makes the reducer total (the
key breaks ties). `verifyEvent` recomputes the id, checks the key matches the
public key, and verifies the signature over
`canonical({v,gid,kind,pub,key,ts,hlc,body,id})`.

On the wire, events travel in an `ENC_EVENT` whose payload is
`{"g":gid,"n":iv,"c":ct,"t":tag}` with the group key and the gid as AAD. A
non-member can relay but not open it.

### Sync

After a handshake, and every 25 s, each side sends:

```json
{"k":"sum","d":{"groups":[{"g":gid,"n":<count>,"h":"<xor of first 8 bytes of each id>"}]}}
```

If digests differ, the peer sends `ids` with its id list; the receiver replies
`get` for what it lacks; the sender replies `events` with those events. `get` is
capped at 2000 ids per message. This is the entire catch-up mechanism — a peer
coming into range after days away gets everything it missed from any member.

Two extra behaviours exist because a community's *membership* has to reach people
even through a relay: on link-up a node broadcasts its membership events, and on
seeing a `join` from someone new it re-broadcasts them (`announceMembership`,
`welcome`). Both are rate-limited per group.

Non-members keep the last 200 sealed packets for 10 minutes (`relayCache`) and
hand them to a peer that connects later. Nothing is decrypted.

## Derived state (`mesh/state.js`)

`materialize(gid, events, meta)` replays events in HLC order and produces:

- `group:<gid>` — `{ id, name, createdAt, ownerKey, admins, members, usernames,
  banned, pins, invite, inviteOnce }`
- `msg:<gid>:general:<ts>:<eventId[:8]>` — messages, polls, system notices
- `post:<gid>:<ts>:<eventId[:8]>` — forum posts with their `replies`

Rules, all enforced by the reducer (there is no server to enforce them):

- Content from a non-member, or from a banned member, is ignored entirely.
- `edit` / `post_edit` / `post_edit_reply` — author only. Polls are not editable.
- `delete` / `post_delete` / `post_delete_reply` — author or admin.
- `react` — one emoji per member per message; the same emoji again removes it.
  Only the 19 `REACTIONS` are accepted.
- `vote` — one per member; `multi` toggles.
- `pin` / `unpin` — admin only; the list is newest-first and capped at 20.
- `name` — first claim wins, 60-day cooldown between renames, old names stay
  reserved. A rename injects a system message derived from the event, so every
  peer writes the same notice.
- `admin` (owner only), `remove` (admin, not the owner), `ban` (owner, permanent),
  `destroy` (owner).
- `join` — refused for banned keys; `once` spends the one-time invite.

Because it is a replay, **never** add a rule that depends on "now" (except the
retention cutoff, which every node applies identically) or on local state that is
not in the log.

## Store

`data/data.json`:

```json
{ "version":1,
  "groups": { "<gid>": { "secret":"<base64url>", "name":"…", "ownerKey":"…", "createdAt":0 } },
  "events": { "<gid>": [ …signed events… ] },
  "meta": {} }
```

`secret` is the group key material and is **never** exposed through the API. The
materialised KV is derived and cached; `addEvent` invalidates the affected group
and the merged KV.

`materialized()` attaches `invite` / `inviteOnce`, derived from the secret, so
every member computes the same code without syncing it.

Retention: `sweep()` runs hourly and drops content events older than 30 days;
`addEvent` refuses them on arrival so nodes converge. Membership and moderation
events are kept forever (they are what the community *is*).

## Local API

Same shapes as Commons, so the UI needed almost no changes.

- `POST /api/account/create` — returns this device's identity (idempotent).
- `POST /api/account/login {key}` — imports an identity key; replaces the device
  identity and drops every link.
- `GET /api/account/session?key=` — valid iff `key` is the current account key.
- `POST /api/group/create|join|invite|claimname|remove|toggleadmin|ban|delete|pin|unpin`
- `POST /api/message/send|delete|edit|react|search`, `/api/poll/create|vote`
- `POST /api/post/create|edit|editReply|delete|reply|deleteReply`
- `GET /api/get|mget|list` — the derived KV (no `account:` namespace exists).
- `POST /api/image/upload`, `GET /api/image/<id>.<ext>`
- `GET /api/node/status` — peer id, transports, peers, group count.

Every mutation needs `key` = the current account key. The API is bound to
127.0.0.1 by default and rejects a request whose `Origin` host does not match its
`Host`, so a random web page cannot drive the node.

## Invariants to keep

1. **Never trust a payload's identity.** Author, id and timestamps come from the
   signed event, never from the request.
2. **Never expose the group secret** through `/api/get|mget|list`.
3. **A packet id must not depend on the TTL.** Relaying depends on it.
4. **AAD must be derivable from the packet** on both sides. Using the receiver's
   identity (an earlier bug) breaks every link.
5. **The reducer must be deterministic.** No `Date.now()` except the retention
   cutoff; no local-only state.
6. **`Store.addEvent` is the only way in.** It is what refuses expired content,
   so all paths (local publish, relay, sync) converge.
7. **Drop the link, don't limp.** A frame that fails to decrypt or a replay means
   the link is not who it says; `drop` it.
8. **Bump `CACHE` in `public/sw.js`** after changing anything in `public/`.

## Bluetooth backend notes

`mesh/transports/ble-bluez.js` uses BlueZ over D-Bus through the optional
`dbus-next` package. It advertises service `c0bb1e00-…-5c0a5b1e7e01` with a write
characteristic (RX) and a notify characteristic (TX), and scans for the same
service to connect out. Characteristics are declared with dbus-next's decorators
applied by hand (`decorate()`), because the library's documented usage needs a
Babel plugin and this project has no build step for the node.

BlueZ's GATT server does not report which central wrote a value, so the peripheral
role accepts **one** inbound central at a time. Frames are chunked with a
`[u16 total][u16 offset]` header (`transports/chunk.js`) so a 20-byte or 517-byte
MTU both work.

If you have hardware, verify: advertise/scan round trip, a 2 KB message over the
real MTU, a reconnect after range loss, and two phones with one relaying.

## Debugging

- `CBT_DEBUG=1 node server.js` — handshakes, frames, sync decisions, event
  rejection reasons.
- Blank page: run `npm run build`; the browser loads `public/app.js`.
- A node with no peers: `--transport ble` on macOS/Windows falls back to LAN; check
  `GET /api/node/status`.
- Messages not arriving: check that both nodes share the group id, then look for
  "event rejected" / "event not stored" in the debug log.
- Tests hang: `tools/app-test.mjs` leaves nodes running if killed with SIGKILL;
  check for stray `server.js` processes before assuming a port is free.
